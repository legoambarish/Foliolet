# Foliolet: trust boundaries and deployment debt

This is a custodial commitment-verification system with an encrypted development vault. It is a locally tested hackathon implementation, not a production security product.

## What a successful proof establishes

* The disclosed canonical value/label/type/derivation metadata belongs to the anchored fact root.
* The platform signed the purpose, intended-verifier label, nonce, expiry and commitment context.
* The registry/operator/chain match externally trusted deployment identity, and the credential is currently active.
* Source assurance is the committed enrollment snapshot, shown separately from mathematical inclusion.

It does **not** independently establish holder authorization for disclosure if the custodial platform is malicious. Disclosure authorization and policy remain enforced by the custodial service. A malicious platform can decrypt a hidden leaf and sign a new presentation against an existing active root; mandatory deployment pins do not prove holder consent. The independent verifier checks cryptographic membership and pinned on-chain credential state.

It also does not establish issuer truth, document creation time, faithful manual extraction, identity of the bearer, holder-key possession, or a private inequality computation. `CGPA at least 8.5=true` is a platform-computed committed boolean from a holder-confirmed number; no ZK range circuit is executed. First-seen tracking is a limited continuity/provenance signal, not independent issuer authenticity.

The trusted deployment identity is provisioned separately in Django's local `WALLET_TRUST_FILE` (default `.local-data/trusted-deployment.json`). The browser never obtains trusted defaults from Spring's `/api/public/network` or the proof. Node requires explicit registry, operator and chain pins. Missing, zero-address, malformed or mismatched pins fail closed; a syntactically valid address is not automatically trustworthy. Trust still depends on how the verifier obtains those pins, the verifier code and the chosen RPC. The demo's one-host trust file is an operator-managed configuration boundary, not protection against compromise of the whole machine.

## Implemented safeguards

Owner checks for wallet data, unpredictable IDs/tokens, hashed bearer tokens, typed canonicalization, random salts, domain-separated hashes, context-bound AES-256-GCM, signed presentation context, active chain checks, immutable version transitions, atomic one-time service release, validated backup restoration, scoped signed watcher records/replay control, safe storage filenames, non-cacheable private/public responses, CSRF-protected Django forms, local vendor assets and a restrictive CSP. Django's `strict-origin` referrer policy exposes only the origin, never a proof-token path, and preserves form POST Origin checks. No analytics or CDN request receives proof tokens.

Extracted suggestions are regenerated from the encrypted original for an unconfirmed draft and are never written to Django sessions. Confirmation stops returning suggestions; leaving/cancelling a review creates no retained suggestion copy. The session migration removes old copies, including expired rows; middleware also removes legacy copies on access. This is logical removal, not forensic erasure of historical SQLite pages or backups. Confirmed encrypted vault records and holder-controlled draft originals remain under the existing retention model.

Django renders/caches a release only after validating the bundle structure and requiring literal `true` for `verified`, proof, signature, anchor, current-state and policy flags. Export repeats these checks and drops rejected cache entries. This is an explicitly labeled **service verification** result; it cannot detect a malicious service that lies consistently. Independent cryptography and service-reported policy have separate displays. Custom labels always carry a holder-authored classification; only the exact recognized path, type, label and derivation metadata receive the platform-derived threshold classification. Both display the canonical metadata.

The shared browser/Node verifier checks the v1 object schema, required native JSON types, bounds and canonical claim values before cryptography. Java's public bundle parser rejects unknown fields, missing fields, primitive nulls, duplicate JSON keys and scalar coercions, including boolean/number-to-string conversion. Shared canonical value vectors test Java/JavaScript agreement. Django also rejects noncanonical claim/path/derivation values before display or export. Java, Django and the independent verifier reject a provenance label inconsistent with its anchored numeric code. Username uniqueness is enforced by a named database constraint, with HTTP 409 handling for conflicts; this does not change case-sensitive username semantics.

## Material remaining limitations

* **Custodial authority:** the server can decrypt documents/claims and create statements. The same relay key anchors credentials and signs presentations. Its compromise can forge platform enrollment; it cannot silently change an already anchored immutable root, but can revoke/supersede states as operator. Separate signing identities/KMS, holder signatures and issuer integrations are future work.
* **Local chain trust:** Ganache is a genuine EVM with actual Solidity transactions, but a single local operator can reset its history. It is not a distributed authenticity guarantee. Public-network deployment, finality/reorg policy, RPC diversity and independent contract publication are not demonstrated. Startup rejects unexpected chain IDs and missing persisted contracts; configured bytecode is not fully matched to a published artifact.
* **Watcher assurance:** HMAC proves the paired agent secret submitted a report. The holder can fabricate reports or disable sampling. No hardware trust, independent timestamp authority or complete offline/change/delete history exists. Enrollment assurance is frozen; later agent revocation does not rewrite its historical snapshot.
* **Sharing:** bearer links are transferable. Labels/purposes bind context but do not enforce recipient identity or downstream use. One-time/expired/revoked links restrict new service releases; retained facts remain readable. Roots, credential IDs, leaf indices/counts and sibling commitments correlate repeated presentations. There is no unlinkability/hidden-path ZK.
* **Authentication:** existing Basic authentication remains; Django stores reusable credentials in server-side sessions. HTTPS, hardened session storage, proper token exchange/password reset and rate limiting are production prerequisites. No self-service ADMIN registration is allowed. Existing admin accounts need a controlled provisioning path.
* **Storage/operations:** development encryption keys reside beside data under `.local-data`; restrictive key ACLs/KMS and rotation were not introduced by this patch. The EVM launcher creates an ignored local relay key; the original audit used a publicly known development key, retained only in the existing local fixture environment. Losing the vault key loses decryptability. Backups beside live files do not cover disk loss. Labels, categories, fact paths, assurance clocks, original-file salt/hash used internally are plaintext in PostgreSQL; per-leaf salts and claim values are inside encrypted leaf records. Introduce separately protected keys/backups, explicit production migrations, retention/deletion controls, encrypted metadata and resource limits before sensitive deployment.
* **Recovery race (audit LOW, unresolved):** backup bytes are authenticated and matched to the commitment before recovery, but installation rereads the path. A concurrent local file replacement can race that check. The existing damage/recovery tests do not prove resistance to a hostile concurrent filesystem writer.
* **First-seen snapshot race (audit LOW, unresolved):** observation ingress is serialized but enrollment does not take the same atomic agent/history snapshot lock. Concurrent ingress/revocation around enrollment has no explicit sequence cutoff. Do not claim complete or independent historical attestation.
* **Availability:** both proof release and startup depend on a reachable EVM. Direct bundle verification remains possible without Spring once the bundle is obtained, but service-link policy needs the service. SQL/EVM recovery is idempotent, not a distributed transaction; a losing replacement draft or encrypted orphan after database failure needs operational cleanup.
* **HTTP hardening:** loopback development binding only; don't expose `runserver`, trust-auth PostgreSQL or development signing keys. Production needs TLS, direct Spring API CSRF/origin protection where browser credentials are usable, proxy host/origin configuration, streamed body and request-rate limits (including chunked requests), malware scanning, no bearer paths in access logs, metrics and secret handling. Startup code-presence checks are not deployed-bytecode identity validation. These audit LOW items remain unresolved. Audit records are mutable application records, not an immutable ledger.
* **Dependencies:** the pinned Solidity/Ganache toolchain has npm audit advisories (10 on the retained toolchain audit, including 1 critical). It is local build/test tooling; it is not served by Django. Replace/update and reassess it for deployment, rather than applying a breaking `npm audit fix --force`. Ganache's optional native µWS module falls back to JavaScript on the installed Node version; tests passed with that fallback. Browser ethers/QR assets are separate local vendor files with licenses.

Unsupported capabilities cannot earn a stronger badge. Solidity currently accepts assurance codes 0 (self) and 1 (first-seen snapshot) only. Issuer-verified enrollment, VC interoperability, OCR/signature validation, mobile capture, arbitrary ZK predicates and public-chain production operation remain explicit future work.
